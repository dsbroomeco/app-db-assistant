# Agents Configuration — DB Assistant

## Project Overview

**DB Assistant** is a cross-platform desktop database manager application targeting Windows and Linux. macOS support is planned as a future development opportunity. It connects to commonly used local and remote SQL and NoSQL databases, provides tabbed views for databases and tables, supports SQL command execution, and offers CRUD operations through shortcuts and context menus.

## Tech Stack

- **Desktop App**: Electron + React 19 (TypeScript)
- **Bundler & Styling**: Vite (renderer, `@shared/*` alias), CSS Modules (`*.module.css`) with theme CSS custom properties in `src/renderer/styles/global.css`
- **Editor & Grid**: CodeMirror 6 (`@codemirror/*`), `@tanstack/react-virtual`
- **Storage & Updates**: Electron `safeStorage` + `electron-store` (encrypted credentials & settings), `electron-updater`
- **Supported Databases**:
  - SQL: PostgreSQL (`pg`), MySQL/MariaDB (`mysql2`), SQLite (`better-sqlite3`), Microsoft SQL Server (`mssql`)
  - NoSQL: MongoDB (`mongodb`), Redis (`ioredis`)
- **Build/Package**: electron-builder (Windows `.exe`/`.msi`, Linux `.AppImage`/`.deb`/`.rpm`; macOS `.dmg` planned)
- **Testing**: Vitest (unit), Playwright (e2e)

## Coding Conventions

- Use TypeScript strict mode across all source files
- Use functional React components with hooks
- Prefer named exports over default exports
- Use `async/await` over raw promises
- Style components with CSS Modules (`*.module.css`) and CSS custom properties from `src/renderer/styles/global.css`
- All database credentials must be stored encrypted at rest — never in plaintext config files
- Sanitize and parameterize all SQL queries — never interpolate user input into query strings
- Use ESLint + Prettier for formatting consistency
- Commit messages follow Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, etc.)

## Agent Guidelines

### When working on the Desktop App (`src/`)
- All database connections must go through the `src/db/` driver layer — never import driver packages directly in renderer code
- Follow the tiered driver interfaces in `src/db/types.ts` (`BaseDriver`, `DatabaseDriver`, `MongoDBDriver`, `RedisDriver`) and register new drivers in `src/db/drivers/index.ts`
- IPC between main and renderer must use typed channels defined in `src/shared/ipc.ts`; keep `src/main/main.ts`, `src/main/preload.ts`, and `src/shared/ipc.test.ts` in sync whenever channels change
- Never expose database credentials to the renderer process
- Connection strings and credentials flow through the main process only
- **Dual TypeScript / CommonJS build constraint**: `tsconfig.main.json` compiles `src/main/`, `src/shared/`, and `src/db/` to CommonJS. Any ESM-only dependency used in main/db (such as `electron-store` and `electron-updater`) **must** be loaded with dynamic `await import(...)`, never a static top-level `import`

### Security Rules (All Code)
- Parameterize all database queries — no string concatenation for SQL
- Escape SQL identifiers using helpers in `src/db/sanitize.ts` (`escapePgId`, `escapeMysqlId`, `escapeMssqlId`) and validate import column types with `isValidSqlType()`
- Sanitize error messages returned to the renderer with `sanitizeErrorMessage()` from `src/db/sanitize.ts`
- Validate and sanitize all user input at system boundaries; enforce home-directory boundaries (e.g., `resolvePathWithinHome()` in `src/main/main.ts`) for file write/export paths
- Store credentials encrypted via Electron `safeStorage` + `electron-store` (`src/db/credential-store.ts`)
- No secrets in source code or config files committed to git
- Escape all user-provided content rendered in the UI to prevent XSS

### Post-Change Checklist (Required After Every Agent Change)

After every code change, agents **must** review and update all affected documentation and config:

1. **README.md** — Update setup instructions, scripts table, project structure, or feature list if they changed
2. **AGENTS.md** — Update conventions, structure, or guidelines if new patterns were introduced
3. **ROADMAP.md** — Mark completed items `[x]`, add new items discovered during implementation
4. **ARCHITECTURE.md** — Update diagrams or design decisions if architecture changed
5. **CONTRIBUTING.md** — Update if workflows, branch conventions, or tooling changed
6. **`.env.example`** — Add/remove/update environment variable entries to match current requirements (never commit actual `.env` files)
7. **Tests** — Add or update unit tests (`*.test.ts` / `*.test.tsx`) for any changed or new code; update e2e tests in `tests/e2e/` if user-facing behavior changed
8. **`package.json`** — Ensure scripts, dependencies, and metadata are accurate

Do not skip documentation updates. Stale docs are worse than no docs.

### Testing & Verification
- Unit tests live next to source files as `*.test.ts` or `*.test.tsx`
- E2E tests live in `tests/e2e/`
- Run verification checks before finishing:
  - `npm run typecheck` — TypeScript check (`tsconfig.json`)
  - `npm run lint` — ESLint across `src/` (`npm run format` for Prettier)
  - `npm test` — Vitest unit test suite
  - `npm run build` — Verifies both `tsconfig.main.json` (CommonJS) and Vite renderer builds
  - `npm run test:e2e` — Playwright E2E suite (for UI/app-launch changes)
- If `better-sqlite3` fails with a native ABI error under Electron, run `npm run rebuild:native`
